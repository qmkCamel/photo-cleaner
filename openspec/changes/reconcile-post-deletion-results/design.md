## Context

当前删除调用链为 `ReviewBinView.deleteSelectedAssets` → `PhotoLibraryDeleting.deleteAssets` → `PhotoDeletionResult` → `CleanupFlowState.applyDeletionResult`。`CleanupFlowState` 是首页、任务复核和复核箱共享的内存状态所有者，但现有成功回写只移除 `reviewBinItems` 并设置布尔值与恢复文案，没有移除 `reviewGroups` 和 `tasks` 中的对应候选。首页总空间又直接由 `tasks` 聚合，因此用户返回首页后仍看到已经删除的候选和旧预计空间。

Photos 删除成功表示项目已从系统照片图库移除并通常进入“最近删除”，不等于系统已经永久回收对应空间。Limited Photos Access 仍是有效状态，删除后的首页仍需保留结果可能不完整的提醒。

删除动作本身继续遵守全局 `user-action-contract`：使用动作局部忙碌状态、避免重复提交，并为失败或中断提供恢复路径。本变更只定义动作完成后的状态协调，不复制该全局契约。

## Goals / Non-Goals

**Goals:**

- 让一次删除结果在共享状态中原子生效，首页、任务复核和复核箱不得互相矛盾。
- 用准确文案区分“已移至最近删除”“预计体积”和“空间已经永久释放”。
- 覆盖全部成功、部分成功、全部失败和重新扫描后的确定性状态。
- 保持 Limited Photos Access、二次确认、默认禁删测试和恢复窗口等信任边界。
- 让状态变化可被 VoiceOver 感知，并支持 Dynamic Type 和非颜色提示。

**Non-Goals:**

- 不改变扫描、分类、置信度、推荐保留和默认选择算法。
- 不在删除成功后自动发起完整扫描。
- 不深链或管理 Photos 的“最近删除”，也不声称能够确认系统何时真正回收存储空间。
- 不持久化跨启动的删除历史，不增加删除撤销 API。
- 不改变 Release 与 Debug 的删除安全策略。

## Decisions

### 1. 由 CleanupFlowState 原子协调所有删除后状态

`CleanupFlowState.applyDeletionResult` 继续作为唯一删除结果入口。处理结果前，状态从 `reviewBinItems` 中按资源 ID 建立待删除候选快照，用于计算成功数量和预计体积；随后在同一次状态变更中完成：

1. 从复核箱移除成功 ID，失败 ID 保留并选中。
2. 从所有 `reviewGroups.candidates` 和 `selectedCandidateIDs` 移除成功 ID。
3. 删除已无可操作候选的复核分组，并从剩余分组重新生成 `tasks`、候选数量、预计体积和预览缩略图。
4. 修正 `currentReviewGroupIndex`，确保空数组和分组减少后不会越界。
5. 累加当前扫描周期的删除摘要，并设置失败信息。

任务重建逻辑应提取为扫描构建器和状态协调共同复用的纯函数，避免分别维护任务标题、置信度、数量和缩略图规则。

替代方案是只修改首页展示层，临时过滤已删除 ID。该方案会让任务复核和复核箱继续读取不一致状态，并增加每个视图重复过滤的风险，因此不采用。

### 2. 使用结构化删除摘要取代布尔成功标记

新增值类型摘要，至少包含当前扫描周期累计成功数量和对应候选预计体积。摘要中的体积来自删除前的候选快照，只能用于“约 X MB”或“预计体积”，不得命名为已释放空间。

摘要在同一轮扫描内累计，支持用户分多批完成清理；新一轮扫描开始时重置。现有 `hasDeletedItems` 和 `postDeletionRecoveryMessage` 应由摘要派生或被摘要替代，避免多个可漂移状态源。

替代方案是每次只保留最后一次删除结果。该方案在多批删除后会低报本轮成果，也无法提供稳定的首页反馈，因此不采用。

### 3. 首页按剩余可操作候选选择完成态或剩余态

删除摘要存在时，首页在标题下优先展示成功摘要：

- 标题：“已移至‘最近删除’”。
- 数据：“X 项 · 约 Y MB”。
- 说明：“这些项目仍可在 Photos 中恢复，空间可能尚未立即释放。”

如果已经没有可操作候选，隐藏“预计可释放空间”和任务卡，展示“本轮没有待复核项目”空态；底部保留“重新扫描”。如果仍有候选，将指标改为“剩余预计可释放空间”，任务数量、缩略图和体积只包含剩余项目。

Limited Photos Access 提示始终保留，并放在删除摘要之后、剩余任务之前。这样先回答“刚才发生了什么”，再说明结果范围限制。

替代方案是把页面标题改成“清理完成”。该标题容易被理解为永久释放空间，也会让首页在有剩余候选时失真，因此页面标题仍保持“扫描结果”。

### 4. 不自动重新扫描，使用显式重新扫描协调外部变化

删除服务已经返回成功资源 ID，立即用这些 ID 协调内存状态，不再触发一次可能耗时的完整扫描。用户从 Photos 的“最近删除”恢复项目、修改权限或在其他设备同步相册后，可使用现有“重新扫描”入口刷新真实状态。

自动重新扫描会延长删除完成反馈、增加取消与并发状态复杂度，也可能让 Limited Access 用户误以为 App 能看到全部相册，因此不采用。

### 5. 自动化只模拟删除结果，真实删除保持单独 opt-in

单元测试直接构造成功、部分成功和失败结果。UI/AppClaw 测试使用确定性的假删除服务或测试启动场景生成结果，同时继续携带禁删开关，不调用 `PHAssetChangeRequest.deleteAssets`。

真机破坏性 smoke 仅使用一张明确可恢复的测试照片，启动时显式启用破坏性删除，验证项目进入“最近删除”后立即恢复，并记录 iCloud Photos 同步风险。禁删开关与破坏性开关同时出现时仍由禁删优先。

## Risks / Trade-offs

- [候选可能在多个派生集合中重复] → 所有协调以唯一资源 ID 集合执行，摘要体积只从复核箱待删除快照按 ID 去重计算。
- [相似组删除后只剩推荐保留项] → 将“是否仍有可操作候选”作为任务保留条件；需要上下文时可以保留分组内部推荐项，但不得继续生成待复核首页任务。
- [部分成功导致索引越界] → 状态协调完成后统一规范化当前分组索引，并为零分组提供安全访问路径。
- [用户把预计体积理解成已释放空间] → 成功态禁止使用“已释放”，明确项目仍在“最近删除”且空间可能尚未立即释放。
- [外部恢复导致内存状态过时] → 不承诺实时监听 Photos 外部变化，保留显式“重新扫描”作为真实状态协调入口。
- [成功提示只靠绿色或视觉位置] → 同时提供图标、明确文本、VoiceOver 状态播报和 Dynamic Type 重排。

## Migration Plan

1. 先增加结构化摘要和纯状态协调逻辑，用单元测试锁定全成功、部分成功、失败和多批累计行为。
2. 再接入首页成功摘要、剩余态、空态和无障碍通知，不改变删除服务接口。
3. 更新安全 UI/AppClaw 测试场景，确保自动回归不触发真实删除。
4. 运行聚焦测试、完整 Xcode 回归、发布预检和 OpenSpec 严格校验。
5. 获得明确批准后执行单张可恢复照片真机 smoke，并立即从“最近删除”恢复。

回滚时可以移除新增摘要和首页展示，同时保留现有删除服务、二次确认和安全策略；该回滚不涉及持久化数据迁移。

## Open Questions

无。成功文案采用“已移至‘最近删除’”，页面标题保留“扫描结果”，外部相册变化通过显式“重新扫描”协调。
