## Context

`ReviewGroupView` 通过 `@Binding` 直接读写 `CleanupFlowState.selectedCandidateIDs`。当前“复核本组全部”只调用 `selectAllCandidatesInCurrentGroup()`；进入分组时又会先恢复默认选择，因此在默认已经全选可清理项的分组中，这次写入不会改变状态，SwiftUI 也没有新的视觉结果可呈现。

该操作仅修改内存中的 ID 集合，预期同步完成且不超过 300ms，不属于长耗时用户动作；不引入新的异步状态或全局进度。

## Goals / Non-Goals

**Goals:**

- 让批量选择的当前状态、下一步动作和点击结果保持一致。
- 只影响当前分组的可选择候选，并持续保护推荐保留项。
- 用状态测试和 UI 截图覆盖“取消全选”和“重新全选”两个方向。

**Non-Goals:**

- 不改变候选识别、默认选择或推荐保留算法。
- 不自动把候选加入复核箱，不改变删除确认流程。
- 不执行真实 Photos 删除。

## Decisions

### 1. 由 `CleanupFlowState` 统一计算并切换全选状态

状态层根据当前分组中所有 `recommendedKeep == false` 的候选生成可选择 ID 集合。如果该集合非空且已经全部包含在 `selectedCandidateIDs` 中，则批量动作移除这些 ID；否则补齐这些 ID。这样视图不复制选择规则，单元测试也能直接覆盖边界。

替代方案是让视图逐项调用单选逻辑，但会把业务状态判断放进 SwiftUI 层，也更难保证推荐保留项不会被误选，因此不采用。

### 2. 按“下一次点击会发生什么”动态展示按钮

当前已经全选时显示“取消全选”，其他状态显示“全选本组可清理项”。点击后候选圆框和主按钮数量由现有绑定立即刷新。相比固定显示“复核本组全部”，动态文案明确表达这是选择动作，不暗示会打开新的复核流程。

### 3. 自动化验证可见结果而非仅验证可点击

XCUITest 必须断言批量按钮文案、主按钮可用状态和数量随两次点击发生变化，并以 `XCTAttachment.keepAlways` 保存取消全选与重新全选结果截图。启动参数继续关闭真实照片删除。

## Risks / Trade-offs

- [用户把“取消全选”理解为删除取消] → 文案限定在当前复核页上下文，且主按钮同步变为“选择项目后加入复核箱”，清楚表示只影响待加入选择。
- [异常状态包含其他分组的选择 ID] → 批量取消只移除当前分组可选择 ID，不清空无关 ID。
- [当前分组没有可选择候选] → 全选状态返回 false，按钮禁用，避免无意义操作；正常任务重建仍会过滤这种分组。

## Migration Plan

无需数据迁移。更新状态方法和视图文案后运行聚焦测试、模拟器 UI 自动化和真机覆盖安装；如需回滚，仅恢复旧批量选择方法和固定按钮文案，不影响持久化数据。
