# 10 当前识别策略

本文档记录当前 iOS MVP 如何识别清理候选，以及后续引入端侧 AI 时应遵守的边界。

核心原则：当前版本只产出“值得复核的候选”，不自动判断“可以删除”。所有候选都必须经过逐组复核、加入复核箱、删除前二次确认，才会请求系统 Photos 删除。

实现入口：

- `iOS/TrueKeep/TrueKeep/Services/PhotoLibraryScanner.swift`
- UI 示例数据在 `iOS/TrueKeep/TrueKeep/Data/SampleCleanupData.swift`，只用于 `-TrueKeepUseSampleCleanupData`、截图和 UI 自动化，不代表真实扫描结果。

## 当前真实扫描范围

扫描只读取用户授权范围内的 Photos 资源：

- Full Access：扫描完整可访问图库。
- Limited Access：只扫描用户授权给 App 的照片和视频，并在 UI 中提示结果可能不完整。
- 隐藏资源不纳入扫描。
- 缩略图和视觉分类请求不允许 iCloud 网络下载，避免为了分类触发云端取图。

当前真实扫描覆盖五类候选：

- 截图和聊天截图。
- 占空间的大视频。
- 短时间内相似照片。
- 疑似误拍。
- 疑似模糊或遮挡。

## 分批和性能边界

扫描按批处理，避免一次性阻塞 UI：

- 标准批大小：`200`
- 低电量模式批大小：`50`
- 标准视觉分类上限：最新 `300` 张非截图照片
- 低电量模式视觉分类上限：最新 `80` 张非截图照片

截图和视频候选来自 Photos 元数据扫描；相似、误拍、模糊候选来自本地图像视觉指标。相似照片优先使用 Vision feature print；质量判断通过本地质量评估接口，当前没有 bundled Core ML 模型时会自动使用确定性的启发式兜底。

## 候选规则

### 截图

使用 Photos 系统 subtype：

- `asset.mediaSubtypes.contains(.photoScreenshot)`

这类候选的解释文案是“系统识别为截图，可能是临时信息。”

### 大视频

当前真实扫描主要按时长判断：

- `duration >= 300` 秒，即 5 分钟以上。

代码也支持未来接入真实文件大小后按大小判断：

- `estimatedBytes >= 500_000_000`，即约 500 MB 以上。

目前视频大小展示仍可能是估算值，不应当对外承诺精确释放空间。

### 相似照片

只处理非截图照片。当前流程：

1. 请求 224x224 本地图像缩略图。
2. 降采样为 32x32 像素。
3. 计算本机视觉指标：Vision feature print、感知 hash、亮度、饱和度、边缘清晰度和质量评分。
4. 按创建时间从新到旧排序。
5. 两张照片满足以下条件时归为相似：
   - 创建时间差不超过 `180` 秒。
   - 如果两张照片都有可比较的 Vision feature print，feature-print distance `<= 0.16`。
   - 如果 feature print 不可用或不可比较，回退到感知 hash 汉明距离 `<= 8`。
6. 如果 Vision feature print 可比较但距离超过阈值，不再用 pHash 把这两张照片兜底分组。
7. 每个相似组内，将本地质量评分最高的一张标为“推荐保留”。

推荐保留项不能加入删除选择。

### 疑似误拍

只对未进入相似组的非截图照片判断。判断入口是本地质量评估：

- 如果 app bundle 中存在编译后的 `TrueKeepPhotoQuality.mlmodelc`，优先使用 Core ML 模型输出的误拍风险分。
- 如果模型不存在或预测失败，使用启发式质量评分兜底。

启发式误拍风险基于以下信号：

- 过暗：亮度 `< 0.11`
- 过亮：亮度 `> 0.92`
- 低饱和且低清晰度：饱和度 `< 0.045` 且清晰度 `< 0.015`

模型或启发式输出的误拍风险达到当前阈值 `0.85` 时，才会标记为疑似误拍。这类结果属于低置信度候选，默认不选中。

### 疑似模糊或遮挡

只对未进入相似组、且未被标为误拍的非截图照片判断。判断入口同样是本地质量评估：

- 如果 app bundle 中存在编译后的 `TrueKeepPhotoQuality.mlmodelc`，优先使用 Core ML 模型输出的模糊风险分。
- 如果模型不存在或预测失败，使用边缘清晰度启发式兜底。

启发式模糊风险会在边缘清晰度较低时升高；风险达到当前阈值 `0.85` 时，才会标记为疑似模糊或遮挡。这类结果属于低置信度候选，默认不选中。

## 默认选中策略

默认选中不是“自动删除”，只是进入逐组复核时的初始选择。

默认选中：

- 截图。
- 大视频。
- 相似组中非“推荐保留”的项目。

默认不选中：

- 疑似误拍。
- 疑似模糊或遮挡。
- 相似组中的“推荐保留”项目。

用户可以在复核页修改选择；推荐保留项被禁用，不能加入复核箱。

## 当前限制

- 没有云端 AI。
- 没有人脸、主体、语义内容、纪念价值判断。
- 不识别“孩子”“宠物”“票据”“证件”等具体语义类别。
- 相似照片已优先使用 Vision feature print，但阈值仍需要真实照片库校准。
- 当前仓库没有 bundled `TrueKeepPhotoQuality.mlmodelc` 模型资产，质量评分会走启发式兜底。
- 误拍、模糊仍是低置信度复核候选，不是高置信删除判断。
- 视觉分类只覆盖最新一部分照片，受低电量模式影响。
- iCloud-only 且本地无缩略图的资源可能不会进入视觉分类。
- 释放空间目前可能是估算，不应作为精确存储统计使用。

## 后续端侧 AI 方向

可以引入端侧 AI，但建议分阶段做，并保持“候选复核”产品原则不变。

### 适合优先引入的能力

1. 校准相似/重复聚类

   当前已接入 Vision feature print 优先路径。后续需要用真实照片库样本校准 `0.16` distance 阈值，并确认低电量模式、老设备和大图库下的耗时表现。

2. 接入真实 Core ML 质量模型

   当前代码已有 `TrueKeepPhotoQuality.mlmodelc` 加载入口和启发式兜底。后续可以提供训练好的模型资产，让模型输出质量、模糊风险和误拍风险分。UI 仍显示“疑似”“建议复核”，不要直接写“可删除”。

3. 相似组最佳保留建议

   结合清晰度、曝光、人脸质量、闭眼、主体完整性，为相似组推荐保留项。建议仍只作为推荐，不允许自动删除其余项目。

4. 解释摘要

   将模型分数转成可解释原因，例如“画面过暗”“主体不完整”“与前后照片高度相似”。解释要来自可核验信号，避免泛泛写“AI 判断”。

### 不建议首批做的能力

- 自动删除。
- 云端上传分析。
- 用语义模型判断“这张照片没有纪念价值”。
- 用黑盒分数默认选中低置信照片。
- 在没有设备分层和能耗测试前全图库跑重模型。

### 建议的上线门槛

引入端侧 AI 前，至少满足：

- 模型只在本机运行，且隐私文案同步更新。
- 有设备能力分层：高性能设备启用完整模型，低性能或低电量模式降级到轻量规则。
- 有耗时动作局部进度，不阻塞其他导航。
- 所有模型候选都有可解释原因。
- 低置信候选默认不选中。
- 有真实设备误删风险评估和人工标注样本回归集。
- App Store 文案不夸大“AI 自动清理”，只承诺“本机识别复核候选”。

## 当前判断

端侧 AI 值得做，但不应该改变 TrueKeep 的信任模型。更好的定位是：

> AI 提高候选质量和解释质量，用户保留最终删除决定权。

短期优先级建议：

1. 先收集真机扫描质量反馈，确认当前启发式规则的误报/漏报。
2. 优先替换相似聚类和模糊评分，因为这两类最容易用端侧视觉特征提升质量。
3. 暂缓语义价值判断，尤其是家庭照片场景里“低质量但有纪念意义”的误删风险很高。
